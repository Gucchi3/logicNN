# logicNN 要件定義書

## 1. 文書情報

- 文書状態: 変更草案（logicNN_core再設計を反映）
- 承認日: 2026-09-12
- 変更日: 2026-09-12（`torchlogix`直接依存を撤回し、`logicNN_core`再設計へ変更）
- 作成日: 2026-09-12
- 対象: 論理ゲートニューラルネットワーク学習ソフトウェア `logicNN`
- 判断記録: `memo.md`

本書は、既存の `logicnn` をベースラインとして再設計する `logicNN` の要件と受入条件を定義する。フォルダ構成、モジュール間インターフェース、JSON スキーマおよび処理図の詳細は、基本設計・詳細設計で定義する。

## 2. 背景と目的

既存の `logicnn` には一貫した仕様書がなく、処理が複数箇所へ分散し、特に `utils/` の責務が分かりにくい。そのため、コードの理解、修正、機能追加および不具合調査が難しい。

`logicNN` の目的は次のとおりとする。

1. 論理ゲートニューラルネットワークを学習・検証・評価できること。
2. 学習済みの最良モデルを論理回路へ変換し、内製する汎用ライブラリ `logicNN_core` を利用して C コードと Verilog コードを生成できること。
3. 仕様書から処理全体、設定、成果物およびコードの配置を把握できること。
4. データセット固有処理と共通処理を分離し、将来のデータセット追加を局所的な変更で行えること。

## 3. 開発と承認の進め方

- ユーザーは草案の提示、改善提案、重要事項の判断および承認を担当する。
- Codex は調査、草案の整理、設計、開発用テスト、実装、レビューおよび工程管理を担当する。
- 要件、基本設計、詳細設計およびテスト設計は、ユーザーの承認後に次工程へ進める。
- コーディングは設計承認後に段階的に行う。

## 4. 対象範囲

### 4.1 初期版の対象

- MNIST の取得、読込、前処理、学習、検証およびテスト。
- MNIST 用論理ゲートニューラルネットワーク。
- ランダム初期値からの新規学習。
- logicNN 形式の `.pth` を初期重みに使用する新規学習。
- 最良モデルと最終モデルの保存。
- 最良モデルからの回路変換、簡略化、回路 JSON、C コードおよび Verilog コードの生成。
- 単一 CPU または単一 GPU での CLI 実行。

### 4.2 対象外

- 旧 `logicnn` の設定、チェックポイント、ログまたは内部 API との後方互換性。
- optimizer、scheduler、epoch および履歴を復元する完全な学習再開。
- 初期版での MNIST 以外のデータセット実装。
- マルチ GPU、分散学習およびクラウド実行。
- GUI、Web 画面および Web API。
- `logicNN_core` の範囲を特定データセットまたはMNISTの固定shapeへ限定すること。
- 利用者による `torchlogix` の個別取得、配置、更新およびセットアップ。
- `torchlogix` を実行時依存、Gitサブモジュールまたは自動取得対象として残すこと。

## 5. システム利用フロー

通常の利用フローは次のとおりとする。

1. 必要に応じて `tools/download_dataset.py` で MNIST を取得する。
2. 利用者が学習設定ファイルを選択する。
3. 利用者が `python main.py` を実行する。
4. システムが設定と必要ファイルを検証する。
5. システムがデータを読み込み、分割し、二値化する。
6. システムがモデルを構築し、任意で保存済み重みを初期値として読み込む。
7. システムが全 epoch を学習し、毎 epoch 検証する。
8. システムが最良モデルと最終モデルを保存する。
9. システムが最良モデルを公式テストデータで一度評価する。
10. `circuit.enabled` が有効な場合、最良モデルから回路成果物を生成する。

## 6. 機能要件

### 6.1 実行と設定

#### FR-RUN-001 通常実行

通常実行は CLI の `python main.py` を起点とし、設定ファイルのパスをコマンドライン引数で指定できること。

#### FR-RUN-002 設定区分

設定は少なくとも `run`、`data`、`model`、`train` および `circuit` に区分すること。

#### FR-RUN-003 厳格な設定検証

未知の項目、型の誤り、不正値、未登録名および存在しない必要パスを、可能な限り学習開始前に検出して明確なエラーにすること。

#### FR-RUN-004 実行環境

`run.device` で単一 CPU、単一 GPU または利用可能なデバイスの自動選択を指定できること。

#### FR-RUN-005 seed

`run.seed` を Python、NumPy、PyTorch、データ分割および DataLoader に適用すること。

### 6.2 データ

#### FR-DATA-001 MNIST 取得

MNIST の取得は `tools/download_dataset.py` で行うこと。`main.py` はデータを自動取得しないこと。

#### FR-DATA-002 データ不足時の扱い

必要なデータが存在しない場合、`main.py` はダウンロード方法が分かるエラーを表示して終了すること。

#### FR-DATA-003 MNIST 分割

公式学習用 60,000 件を、`run.seed` に基づいて学習用 50,000 件と検証用 10,000 件へ分割すること。利用者向けの `validation_size` は設けないこと。

#### FR-DATA-004 評価用データ

検証では検証用 10,000 件をすべて使用すること。公式テスト用 10,000 件は学習とモデル選択に使用せず、最良モデル決定後にすべて使用すること。

#### FR-DATA-005 二値化

MNIST は `float32` の `[0, 1]` テンソルへ変換した後、画素値が 0.0 より大きい場合を 1、それ以外を 0 とすること。二値化はデータ前処理で共通適用し、モデル層では行わないこと。

#### FR-DATA-006 データセット拡張構造

`data.name` で登録済みデータセットを選択し、データセット固有の読込、前処理、クラス名および入力形状を専用モジュールへ分離すること。新しいデータセット用モジュールと設定の追加によって、共通の学習・評価・保存処理を変更せず切り替えられる構造にすること。

### 6.3 モデル

#### FR-MODEL-001 モデル選択

`model.name` で登録済みモデルを選択すること。データセットとモデルの組み合わせが不適合な場合は学習開始前にエラーにすること。

#### FR-MODEL-002 モデル構造の定義元

モデル構造を決定する値は対応するモデル定義ファイルだけに記述し、利用者向け設定に `model.parameters` を設けないこと。

#### FR-MODEL-003 MNIST モデルの入出力

モデルは二値化済みの `[batch, 1, 28, 28]` を受け取り、数字 0〜9 に対応する `[batch, 10]` のスコアを返すこと。

#### FR-MODEL-004 MNIST モデル構造

MNIST モデルは次の構造とする。

1. `LogicConv2d`: 16 カーネル、木の深さ 2、受容野 3×3。
2. `OrPooling2d`。
3. `Flatten`。
4. `LogicDense`: 4,000 ノード。
5. `LogicDense`: 4,000 ノード。
6. `GroupSum`: 10 クラス、`tau=8`。

#### FR-MODEL-005 論理演算方式

学習時は `logicNN_core` の連続緩和された論理演算を使用し、検証、テストおよび回路変換時は離散化された論理演算を使用すること。

### 6.4 学習

#### FR-TRAIN-001 学習設定

epoch 数、損失関数、optimizer および learning-rate scheduler と、それぞれに必要な値を設定ファイルで指定できること。

#### FR-TRAIN-002 初期対応方式

初期版では、損失関数に交差エントロピー、optimizer に AdamW、scheduler に Cosine Annealing を指定できること。設定は `train.loss`、`train.optimizer` および `train.scheduler` に分け、それぞれに `name` を持たせること。

#### FR-TRAIN-003 学習回数

Early Stopping は行わず、設定された全 epoch を学習すること。

#### FR-TRAIN-004 検証

現行 `logicnn` と同様に、毎 epoch の学習後に検証データ全件で評価すること。検証間隔の設定は設けないこと。

### 6.5 初期重み

#### FR-WEIGHT-001 読込方式

`initial_checkpoint_path` が `null` の場合はランダム初期値から学習し、logicNN 形式の `.pth` が指定された場合はその重みを初期値として新しく学習すること。

#### FR-WEIGHT-002 新規学習としての扱い

重みを読み込んだ場合も、optimizer、scheduler、開始 epoch および過去の学習履歴は復元しないこと。epoch と履歴は 1 から開始し、新しい実行ディレクトリへ保存すること。

#### FR-WEIGHT-003 対応形式

正式に受理する形式は、モデル再構築用メタデータを含む logicNN 形式の一つに限定すること。`model_best.pth` と `model_final.pth` は同じ形式とし、どちらも初期重みに指定できること。

#### FR-WEIGHT-004 不整合

チェックポイントの重みまたはメタデータが選択したモデルと一致しない場合、学習開始前にエラーにすること。

### 6.6 モデル選択とテスト

#### FR-EVAL-001 最良モデル

検証精度が最も高い epoch のモデルを最良モデルとすること。同率の場合は先に記録された epoch を採用すること。

#### FR-EVAL-002 最終モデル

最終 epoch 終了時点のモデルを最終モデルとすること。

#### FR-EVAL-003 公式テスト

全 epoch 終了後に最良モデルを復元し、公式テストデータ全件で一度だけ評価すること。

### 6.7 成果物

#### FR-OUT-001 実行ディレクトリ

1 回の実行ごとに `log/YYYYMMDD_HHMMSS/` を基本とする一意なディレクトリを作成し、過去の実行結果を上書きしないこと。

#### FR-OUT-002 必須成果物

通常学習では次のファイルを保存すること。

- `config.json`: 実際に使用した設定。
- `training_info.json`: モデル構造、データセット、前処理および実行環境。
- `metrics.jsonl`: epoch 番号、学習率、学習損失、学習精度、検証損失および検証精度。
- `curves.png`: 学習損失、検証損失および検証精度の推移。
- `model_best.pth`: 検証精度が最良のモデル。
- `model_final.pth`: 最終 epoch のモデル。
- `test_metrics.json`: 最良モデルによる最終テスト結果。

#### FR-OUT-003 メタデータ

実際のモデル構造と主要定数は `training_info.json` と両チェックポイントへ記録すること。二値化方式と閾値を含む前処理情報も記録すること。

### 6.8 回路出力

#### FR-CIRCUIT-001 制御

`circuit.enabled` の単一スイッチで、回路変換とすべての回路成果物生成を制御すること。個別の `simplify`、`get_c_code` および `get_verilog_code` 設定は設けないこと。

#### FR-CIRCUIT-002 有効時の処理

有効な場合は最良モデルを回路へ変換し、常に簡略化した後、`circuit_simplified.json`、`circuit.c` および `circuit.v` を保存すること。JSONとCはGroupSumを含む完全な回路を表し、VerilogはGroupSumによる加算、`tau`による除算および`bias`加算を含めず、最終論理層までの生の論理出力を出力端子へ接続すること。

簡略化とJSON保存・再読込を通して、集約前の出力数・順序・値を維持すること。定数や同じ信号の重複出力を省略せず、coreが回路構築時に保存した論理出力対応表を利用すること。

#### FR-CIRCUIT-003 無効時の処理

無効な場合は回路変換と関連成果物の保存をすべて行わないこと。

#### FR-CIRCUIT-004 対応範囲

回路変換とC生成の正式対応範囲、および最終集約を除くVerilog生成の正式対応範囲は、`logicNN_core` の版ごとに公開する対応能力表で定義すること。Verilogへクラススコア加算回路を搭載する予定は設けない。torchlogixで有用だったその他の機能は原則として維持対象とし、未実装項目を黙って削除しないこと。

### 6.9 端末表示

#### FR-UI-001 表示方式

端末表示には Rich を使用すること。

#### FR-UI-002 表示内容

学習開始時に実行条件、各 epoch に学習・検証結果、終了時に最良 epoch、最終テスト結果および成果物保存先を読みやすく表示すること。

## 7. 非機能要件

### NFR-001 保守性

`main.py` は処理の起点と全体制御に限定し、設定、データ、学習、評価、保存、表示および回路変換を責務別に分離すること。`utils/` 直下を雑多な共通関数置場にしないこと。

### NFR-002 拡張性

データセット固有処理、モデル定義および方式別の損失関数・optimizer・scheduler を登録単位で分離し、共通ワークフローへの条件分岐追加を最小限にすること。

### NFR-003 再現性

同一の設定、seed、データ、依存関係、デバイスおよび実行環境で、データ分割、データ順序および学習結果を再現できることを目標とする。異なる環境または CPU／GPU 間の完全なビット一致は保証しない。

### NFR-004 可観測性

利用者が設定、モデル、データ、学習経過、最終結果および保存先を Rich の端末表示と成果物から確認できること。

### NFR-005 エラーの明確性

利用者が修正方法を判断できるように、原因となった設定項目、パス、登録名または不整合内容をエラーメッセージに含めること。

### NFR-006 依存関係

論理ゲートNN基盤は `utils/logicNN_core/` に独立したPythonパッケージとして配置すること。logicNNと一緒に配布しつつ、logicNN固有の設定、データ、学習およびログへ依存させず、将来はディレクトリ単体で配布できること。torchlogixは基礎資料と比較対象に限定し、実行時依存にしないこと。

### NFR-007 文書サイト

要件、設計、テスト仕様および検証結果は Docusaurus の docs-only サイトとして管理すること。構成図、アクティビティ図およびシーケンス図は Mermaid で表示できること。

## 8. 開発用テストと運用版

1. 開発用自動テストは実装、変更、レビューおよび受入確認のときだけ明示的に実行する。
2. `python main.py` の通常実行から開発用テストを呼び出さない。
3. 受入確認後、開発用テストコードは運用版の `logicNN` から削除する。
4. テスト仕様と最終検証結果は Docusaurus の文書として保存する。
5. 設定、必要ファイル、データ、モデルおよびチェックポイントの入力検証は製品機能として運用版にも残す。

## 9. 受入条件

### AC-001 通常学習

MNIST を用意した環境で `python main.py` を実行し、ランダム初期値から全 epoch の学習、毎 epoch の検証、最良モデルによる最終テストおよび必須成果物保存を完了できること。

### AC-002 初期重み

`model_best.pth` と `model_final.pth` のそれぞれを初期重みに指定して、新しい実行として学習を完了できること。

### AC-003 回路出力

`circuit.enabled` が有効な場合に、簡略化済み回路JSON、完全なCコード、および出力加算を含まないVerilogコードを生成できること。Verilogの出力端子が最終論理層の生の論理値と一致し、GroupSumの加算、tauおよびbiasを含まないこと。無効な場合はこれらを生成しないこと。

### AC-004 入力検証

不正な設定、データ不足、未登録名、および不適合なデータ・モデル・チェックポイントを、可能な限り学習開始前に検出できること。

### AC-005 精度維持

同じ設定、seed、デバイス、依存関係および実行環境で現行 `logicnn` と比較し、MNIST のテスト精度低下が 1 パーセントポイント以内であること。

### AC-006 文書と運用版

テスト仕様と最終検証結果が Docusaurus の文書として保存され、運用版から開発用テストコードが削除されていること。

## 10. 制約とリスク

- torchlogixから再設計する際に数値挙動、APIまたは回路出力が変化する可能性があるため、固定入力による等価性と承認済み差分を記録する必要がある。
- 現行 `logicnn` の独自Verilog出力加算、scaleおよびsigned score対応は、加算回路が大きくなるため維持対象から除外する。Verilogは最終論理層の生出力だけを担当し、クラススコアの集約は外部回路またはsoftwareの責務とする。
- 開発用テストコードを運用版から削除するため、将来の改修時には本書とテスト仕様を基にテストを再作成する必要がある。
- Windows は通常、大文字・小文字だけが異なる `logicnn` と `logicNN` を同じ親フォルダへ同時に作成できない。旧版を比較用に残したまま新版を実装するための作業用フォルダ名と、受入後の切替方法を基本設計で定める。
