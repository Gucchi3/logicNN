# logicNN 仕様書

このセクションは、logicNNが満たす要件、システム全体の構成、内部処理、成果物および検証方法を定義する。利用方法を説明するスタートアップガイドやユーザーガイドとは分離し、実装とレビューの判断基準をここに集約する。

:::info 現在の文書構成
現在は仕様を順番に決定する設計工程のため、要件定義、基本設計、詳細設計という工程単位で管理している。実装と検証の完了後、内容を失わないように保ちながら、設定、データ、モデル、学習、成果物、回路出力など、サイト利用者が目的から探せる単位へ再編集する。
:::

## 読む順番

1. [要件定義](./requirements.md): logicNNが何を実現し、何を対象外とするかを確認する。
2. [基本設計](./basic-design.md): システム構成、責務分割、依存方向およびシステム単位の処理フローを確認する。
3. [詳細設計](./detailed-design.md): 設定、データ型、関数、学習処理、成果物およびエラー処理を確認する。
4. [テスト仕様](./test-specification.md): logicNN全体の要件と詳細設計をどのように検証するかを確認する。
5. [logicNN_core再設計](./logicnn-core/index.md): 汎用論理ゲートNNライブラリの要件、基本設計、詳細設計および専用テスト仕様を確認する。
6. [実装・検証記録](./verification.md): 現在の実装と実行済みの検証結果、未実施の受入項目を確認する。最終受入結果とは区別する。
7. [受入の現在地](./acceptance-status.md): 合格、検証中、判断待ち、未実施を利用手順ごとに確認する。

## 文書の更新原則

- 要件変更は、基本設計、詳細設計およびテスト仕様への影響を確認して反映する。
- システム単位の関係と流れは基本設計、関数内部の分岐とループは詳細設計に記載する。
- 単純な関数に図を追加せず、分岐、反復または複数モジュール連携があり、文章だけでは追いにくい処理を図示する。
- API文書は実装された関数とdocstringを正本として実装後に作成する。

## 最終的なサイト整理

現在の3文書をそのまま最終サイトの3ページにはしない。docs作成工程では、確定した仕様を次の入口から参照できるように組み替える。

1. はじめに: 目的、対象範囲、全体像
2. システム構成: フォルダ、モジュール責務、依存方向
3. 設定: 設定項目、型、制約、検証
4. データ: MNIST、前処理、分割、DataLoader
5. モデル: builder、共通契約、MNISTLGN構造
6. 学習と評価: epoch、検証、テスト、最適化方式
7. チェックポイントと成果物: 保存形式、読込、実行ディレクトリ
8. 回路出力: logicNN_core境界、簡略化、JSON、C、Verilog
9. logicNN_core: 論理演算、LUT、接続、層、回路IR、独立配布
10. エラー処理: 実行前検証、表示、終了コード
11. 品質保証: 受入条件、テスト仕様、検証結果、要件対応表

同じ説明や図を複数ページへ複製せず、一つの正本へ集約して他ページからリンクする。
